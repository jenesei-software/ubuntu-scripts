# Coolify Node Module

The `coolify-node/` module prepares a server so the Coolify panel can manage it. Run it on the
**managed server**, not on the panel. It reads only `coolify-node/.env` by default.

It does not install Docker or a proxy: the panel does that itself through the access this module
grants.

## What It Does

`setup-coolify-node.sh`:

* validates the public key, the user name and the SSH port before touching anything
* creates an unprivileged user with a home directory and adds it to the `sudo` group
* authorizes the panel's public key in `~/.ssh/authorized_keys`, keeping existing keys and taking a
  backup before the first change
* writes `/etc/sudoers.d/90-coolify-node` with `NOPASSWD`, checks it with `visudo` and only then
  moves it into place
* verifies that passwordless sudo actually works as that user
* reports whether UFW allows the SSH port and whether sshd accepts public keys

The script is idempotent: a second run changes nothing and reports that everything is in place.

`check-setup.sh` verifies the same state without changing anything and exits nonzero when a required
check fails.

## Requirements

* Ubuntu 24.04 with root access
* a public key generated by the panel
* SSH reachable from the panel on the port you plan to use

## Why a Separate User

Coolify logs in as this user, installs Docker, starts the proxy and manages containers. Running the
panel as `root` would give it the whole machine with no audit trail; running it as an unprivileged
user with targeted `NOPASSWD` sudo is the documented approach. The sudoers entry lives in its own
drop-in file, so removing the access is removing one file.

## Prepare Env

In the panel: **Settings → Keys & Tokens → + Add**, name the key, save, and copy the **public** key it
shows (the private half stays inside Coolify and is never printed).

On the managed server:

```bash
cd ~/ubuntu-scripts/coolify-node
cp env.example .env
nano .env
```

```env
COOLIFY_SSH_PUBLIC_KEY=ssh-ed25519 AAAA... panel
COOLIFY_USER=coolify
COOLIFY_SSH_PORT=
COOLIFY_ALLOW_SUDO_NOPASSWD=true
```

* `COOLIFY_SSH_PUBLIC_KEY` — the public key from the panel. Required.
* `COOLIFY_USER` — the login user. Must not be `root`.
* `COOLIFY_SSH_PORT` — the port the panel should use. Empty reads the first `Port` from `sshd -T`.
* `COOLIFY_ALLOW_SUDO_NOPASSWD` — `false` leaves the server reachable but not deployable.

## Run

```bash
bash setup-coolify-node.sh
bash check-setup.sh
```

A different env file can be passed explicitly:

```bash
bash setup-coolify-node.sh /root/coolify-node.production.env
```

## Then in the Panel

**Servers → + Add**:

| Field | Value |
|---|---|
| Name | anything, for example `server-c` |
| IP Address | the server address |
| Port | `COOLIFY_SSH_PORT`, or the port printed by the setup run |
| User | `COOLIFY_USER` |
| Private Key | the key whose public half you put in the env file |

Then **Validate**. When Docker and SSH both report success: **Docker → Install Docker**, and
**Proxy → Start Proxy**.

## Verify

```bash
bash check-setup.sh

id coolify
sudo -l -U coolify
ls -la /home/coolify/.ssh
runuser -u coolify -- sudo -n true && echo "sudo ok"
ssh -p 22 coolify@localhost true
```

The last one proves the login works locally; the panel's own **Validate** proves the key is wired to
the right port.

## Firewall

The module opens nothing. The SSH port must already be allowed, either by the `ubuntu/` module or by
your provider firewall. If `check-setup.sh` reports `UFW shows no allow rule`, fix it in `ubuntu/`
rather than here.

## Rollback

```bash
rm -f /etc/sudoers.d/90-coolify-node
userdel -r coolify        # removes the user and its home directory
```

Removing the sudoers drop-in first revokes the panel's ability to change the machine; delete the
server in Coolify before removing the user, otherwise the panel keeps retrying a dead connection.

## Notes

* Existing keys in `authorized_keys` are preserved; each modification leaves a timestamped backup
  next to the file.
* `COOLIFY_ALLOW_SUDO_NOPASSWD=false` is useful for a server that should only be readable through
  SSH, but the panel cannot deploy to it.
* The module never edits `/etc/ssh/sshd_config` and never reloads sshd: key authorization does not
  need a restart, and changing SSH settings blindly is how access is lost.
* If the panel cannot connect, check in this order: port, user name, key, UFW/provider firewall.
